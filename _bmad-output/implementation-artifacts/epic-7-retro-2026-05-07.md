## What Went Well

### 1. Design Documents Were Accurate & Complete
The architecture from Epic 5 and design docs (supervision-design.md, daemon-design.md) gave the implementation team a clear blueprint. No architectural rework or debates during development — tasks were well-specified from day one.

### 2. Bug Detection via Test Design
Two production bugs were caught **during Story 7.3 test design**, not during production use:
- `int()` cast on supervision interval (would cause infinite spin at sub-second intervals)
- Hardcoded TCP timeout constant (made tests impractically slow)

Both were critical but trivial to fix. The discipline of writing end-to-end tests revealed assumptions that unit tests missed.

### 3. Efficient Test Coverage
- 78 new tests across Levels 2 and 3
- No flaky tests in CI
- All edge cases covered (strike escalation, TCP reconnect, recovery paths, ring buffer throttling)
- Test suite now robust enough for future confidence in supervision system

### 4. Guard Implementation Pattern Worked
Stories 7.1 and 7.2 involved adding guards to prevent race conditions:
- `_sm1_t3_fired` reset rules (prevents duplicate T3 notifications)
- D-3 dual-task guard (prevents two TCP reconnect loops from spawning)
- State regression guard (late callbacks can't regress terminal states)

All guards were documented precisely in story files. Implementation was clean, no follow-up patches needed.

### 5. Feedback Integration from Prior Epics
Epic 6 (PHP core) generated findings about `send_to_jeedom` mocking. Story 7.1 immediately updated 4 test files to apply those lessons. The feedback loop worked.

## Challenges & Growth Areas

### 1. Complexity Concentration
Supervision health monitoring is the single most complex subsystem in the daemon. The 3-strike escalation, TCP reconnect with retries, SM1/SM2 coordination, and ring buffer throttling all had to work together perfectly. One misconfiguration could cause cascading failures.

**Mitigated by:** Detailed design docs + adversarial reviews (27 findings caught before merge).

### 2. Race Condition Prevention
The dual-task race (D-3) and state regression issues required guards at precise points in the code. These aren't obvious without deep state machine knowledge.

**Handled by:** Design docs called out the race conditions explicitly, so implementation didn't have to discover them empirically.

### 3. Test Infrastructure Complexity
Level 3 tests required port allocation, CSR simulator lifecycle management, and poll-with-timeout patterns instead of fixed sleeps. More complex than Level 2, but necessary for true end-to-end validation.

**Mitigated by:** Clear conftest.py patterns + helper functions (`_wait_for`, port finders).

## Key Insights & Lessons Learned

### 1. Design-Driven Development Pays Off
This epic could have been twice as long if the architecture wasn't settled first. Because supervision-design.md specified exact state transitions, error codes, and logging patterns, the implementation was straightforward.

**Takeaway:** Invest in architecture early. It's not overhead — it's the foundation that enables fast, confident execution.

### 2. Test-Driven Discovery of Bugs
The two production bugs were found **before** they could escape to production. The discipline of writing comprehensive E2E tests (Level 3) caught things that unit tests (Level 1/2) couldn't.

**Takeaway:** Don't skip E2E testing as "too slow" — it catches integration issues that mock-based tests miss.

### 3. Guard Patterns are Worth Documenting
The D-3 dual-task guard and state regression guard could become architectural patterns for other features that need to prevent concurrent task spawning or state regressions.

**Takeaway:** When you solve a race condition, document the pattern for reuse.

### 4. Ring Buffer Throttling Works Well
The 10-minute throttle for routine supervision ACKs prevents database spam (1,440 → 144 writes/day) while still capturing important state transitions. Verified to work as designed.

**Takeaway:** Throttling with first-entry bypass is a good pattern for high-frequency telemetry.
