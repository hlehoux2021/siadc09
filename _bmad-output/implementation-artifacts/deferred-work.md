- **D-67: A routine CL/OP overwrites the widget state of an earlier FAILED alarm.** The SM2 state is single-slot (`daemon.py:1451`), so a red FA/PA/BA "Sans réponse" is replaced by "Armement/Désarmement … Confirmée" on the next arm or disarm, and `event_state==1` now fires on every arm and disarm. A scenario that reads `event_state==1` as "alarm confirmed" would misfire. Pre-existing design, already true for BC/OP since 13-1; 13-4 makes it happen much more often.
- **D-68: The EVENT_FAILED notification can print "(utilisateur: None)".** `context.get('user_number', '<inconnu>')` (`error_handler.py:428`) returns None when the key exists with a None value. Pre-existing (13-1). **Fixed 2026-09-26 (13-1 code review): explicit `is not None` check instead of relying on `dict.get`'s default.**
- **D-69: Feminine "Confirmée" on masculine labels.** `event_label` (`daemon.py:789`) reads "Armement/Désarmement (utilisateur N) : Confirmée par la centrale", while the notification side handles agreement correctly. Pre-existing since 13-1's OP.
- **D-70: Nothing warns when `arm` isn't wired after an upgrade.** `siaDC09_update()` creates the command, but an installer who doesn't wire it gets OP on every disarm and never a CL, with no log line or health warning. Only the wizard help text mentions it. Same pattern as 13-1's wiring requirement.
- **D-71: The `siaDC09_update()` loop has no error handling.** A `cmd->save()` exception (for example, a user-created command already named "Armement") stops the loop, and later eqLogics don't get their new commands (`plugin_info/install.php:27-29`). Pre-existing. **Fixed 2026-09-26 (13-1 code review): each `postSave()` call is now wrapped in its own try/catch, logging and continuing rather than aborting the loop.**

## Deferred from: code review of 13-1-burglary-restore-cancel-events (2026-09-26)

- **D-72: `disarm`'s two `sendToDaemon()` calls (BC then OP) have no atomicity, and `_purgeOpenAlarms('BA')` runs regardless of whether either send actually succeeded.** `sendToDaemon()` is a fire-and-forget local-socket write (`siaDC09.class.php:465-482`) — the same pattern used by every command in the plugin (burglarAlarm, prefetchEvent, etc.), not something 13-1 introduced. A process death or exception between the BC and OP calls would leave a BC sent but no OP, with no retry signal, and the purge already happened either way. Not fixable without a project-wide IPC redesign — same class as D-49 (lost-update race in `getCache()`/`setCache()`).
- **D-73: A theoretical race between `disarm` and `alarmReset` firing close together could double-emit BC.** `_purgeOpenAlarms('BA')` relies on "whichever of disarm/alarmReset runs first purges the matching entries" (comment, `siaDC09Cmd.class.php:196-198`), guaranteed today by the alarm plugin's own documented release-before-raz ordering (`alarm.class.php:703-712`). If that ordering guarantee is ever wrong or removed upstream, both commands could observe the same open BA and each emit their own BC. Same risk class as 14-2's D-52/D-53 (accepted as low-likelihood given an existing ordering guarantee, not engineered against directly).
- **D-74: The global `sia_user_number` means every household member disarms under the same SIA address.** ADR-18's own rationale ("Le plugin Alarme ne transmet jamais l'identité de l'utilisateur Jeedom qui désarme") is a disclosed Jeedom-platform limitation, not an oversight — the alarm plugin has no per-actor identity to read. A monitoring center cannot distinguish which household member triggered a given BC/OP/CL from the SIA frame alone. Not fixable without an upstream alarm-plugin change.
- **D-75: `alarmReset`'s "no open alarm" case is logged at debug level only, and collapses two materially different states** — "disarm already purged it" (BA closed a moment earlier via the normal path) vs. "nothing was open" (a spurious raz) are indistinguishable from the log alone, making field diagnosis of a missing BC on a real mode-change reset harder than necessary.
- **D-76: `build_notification()`'s French grammatical-gender agreement is hardcoded per-SIA-code with single-character flags** (`_event_gender_e`, etc.) — fragile: any future SIA code addition needs its own hand-picked flag with no test proving an unrecognized code doesn't produce broken French agreement.

## Deferred from: implementation of 14-4-best-effort-alarm-media-forced-capture (2026-09-27)

## Deferred from: code review of 14-4-best-effort-alarm-media-forced-capture (2026-09-27)

- **D-79: A failed `_writePrefetchPlaceholder()` write combined with a failed daemon create (no callback ever sent for that run) leaves a stale hit from an earlier, unrelated trigger sitting in the cache indefinitely.** `_writePrefetchPlaceholder()` (`core/class/siaDC09Cmd.class.php`) wraps its own read-modify-write in a try/catch that swallows and logs any exception, per the "never block sendToDaemon()" life-safety framing. If that write throws *and* the daemon's forced-capture create call also fails to ever produce a callback for this run (Frigate down, refused), no write ever lands for this run — the previous, unrelated trigger's entry (rank/found/event_id) survives untouched. Deferred (Herve's call, 2026-09-27, code review): needs two independent failures at the same time; same acceptance pattern as D-77 (single shared cache key). If revisited: retry the placeholder write once before giving up, or have `_run_prefetch()` send an explicit rank-4 callback immediately after a create failure (today it only does so at the very end of the run, if nothing better was ever found).

- **D-78: `EVENTS_QUERY_LIMIT = 20` with no server-side label filter could theoretically let a saturation of manual `alarm` events crowd a real detection out of the fetched page.** `_query_candidate_events()` (`resources/siadc09d/frigate_prefetch.py`) requests the most recent 20 `/api/events` rows on the camera, unfiltered by label, then drops manual events client-side. A camera with many trips within the 30s `after` window (a bouncing sensor, or several zones sharing one camera) could in theory fill all 20 slots with manual `alarm` events, pushing a genuine real detection outside the fetched page before the client-side filter ever sees it. Deferred (2026-09-27, code review): low-likelihood — it needs roughly 20 trips inside 30 seconds — and no test exercises this saturation scenario. If revisited: raise `EVENTS_QUERY_LIMIT`, or query with a higher limit and stop scanning once enough real candidates are found.

- **D-77: `sia_prefetch_cache` stays a single shared cache key across all cameras, not one key per camera.** Jeedom's `eqLogic::getCache()`/`setCache()` are themselves a read-then-write of one shared blob per equipment (`core/class/eqLogic.class.php:2040-2047`, verified in Jeedom core source), so even a per-camera key would only narrow, not remove, a lost-update race between two concurrent writers on the *same* camera: `siaDC09Cmd::execute()`'s placeholder write (in the alarm-plugin's PHP process) and `siaDC09::_handlePrefetchResult()`'s callback write (in the daemon-callback PHP process). Story 14-4 (ADR-17 Amendment 4) explicitly kept the single key, accepting this residual window — it only matters when two different cameras' triggers land within milliseconds of each other, and 14-4's `run_id`/rank monotonic rule (D-52, resolved) already protects same-camera ordering. If revisited: split `sia_prefetch_cache` into `sia_prefetch_cache_{cameraEqLogicId}`, updating `_readPrefetchCacheEntry()`, `_writePrefetchPlaceholder()` and `_handlePrefetchResult()` together.
