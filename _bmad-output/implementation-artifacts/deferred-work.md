## Deferred from: code review of 14-2-frigate-event-prefetch-immediate-action (2026-09-24)

- **D-49: Lost-update race in Jeedom's `getCache()`/`setCache()` (single unguarded read-modify-write blob per eqLogic)** — verified in Jeedom core `cache.class.php`: no locking anywhere. Concurrent writers to the siaDC09 eqLogic's cache (e.g. a `prefetch_result` callback racing `_recordOpenAlarm()`) can silently lose each other's updates. Pre-existing pattern already shared by `sia_open_alarms` in the same file (`siaDC09Cmd.class.php`), not introduced by story 14-2; not fixable without a project-wide Jeedom cache-access redesign.
- **D-50: No format validation on the cross-plugin `config::byKey('URL'|'port', 'frigate')` read** — a theoretical "double-scheme URL" if the Frigate plugin ever stored a full URL instead of a bare host would silently break every prefetch (each request becomes `http://http://...`, swallowed by the broad network-error catch, degrading to a permanent, silent miss). Live-confirmed the actual stored value is a bare host with no scheme, so this hasn't manifested. Deliberate scope decision (Dev Notes, story 14-2): avoids a hard class dependency on the Frigate plugin by reading its raw config keys instead of calling its own `getUrlFrigate()` helper — validating against an unspecified third-party plugin's config format was accepted as out of scope.
- **D-51: `sia_prefetch_cache` has no TTL-based pruning/max-size sweep** — unlike `sia_open_alarms` in the same file (`siaDC09Cmd.class.php`), which has an explicit TTL + max-size eviction loop. Bounded in practice by the number of Frigate cameras ever mapped across the plugin's lifetime (small), so low urgency — a future hygiene item if camera churn ever becomes significant.
- **D-52: No dedup/cancellation for concurrent same-camera `prefetchEvent` triggers** — a second trigger on the same camera (bouncing sensor, or two zones mapped to the same camera) spawns a new `_run_prefetch()` task with no cancellation of an in-flight one for the same `camera_eqlogic_id`; PHP's `_handlePrefetchResult()` overwrites unconditionally, so whichever callback lands *last* wins regardless of which trigger it actually answers. Raised as a decision-needed finding, **deferred by Herve (2026-09-24)**: accepted as-is — the window needed to trigger it is narrow (two same-camera prefetches within ~31s), and the alarm plugin's own trigger-delay/sustain settings already discourage sensor bounce. If revisited: track `_run_prefetch` tasks by `camera_eqlogic_id` in `daemon.py`'s `on_message()`, cancel any pending one before spawning a new one for the same camera.
- **D-53: Tight margin between the prefetch's worst-case completion time (~31s) and the alarm plugin's configurable trigger delay** — a short installer-configured trigger delay (e.g. 20-30s) could make `burglarAlarm` fire before the daemon reports back, indistinguishable in the logs from a genuine Frigate miss; siaDC09 has no way to read the alarm plugin's per-zone delay to warn about this. Raised as a decision-needed finding, **deferred by Herve (2026-09-24)**: accepted as-is. If revisited: add a minimum-recommended-delay note to the Step 3 wizard guidance, or reduce `PREFETCH_MAX_WAIT_S` at the cost of missing slower-to-appear Frigate events.
- **D-54: `_query_latest_person_event()` has no trigger-time correlation — a second, unrelated person event within the 30s `after=` window can have its snapshot attached instead of the actual intruder's.** The query is `camera + label=person + after=<now-30s> + sort=desc + limit=1`, so it returns whichever `person` event is most recent in that window, not necessarily the one this specific alarm trigger caused — a narrower recurrence of the exact "wrong photo never is" risk ADR-17/Option D was built to eliminate for species mismatch. Raised as a decision-needed finding in a second review pass (2026-09-24, after story 14-2 had already moved to done), **deferred by Herve**: accepted as-is, same spirit as D-52/D-53 — the 30s window plus the narrow-FOV one-camera-per-zone deployment assumption makes a second distinct person event in-window unlikely in practice. If revisited: correlate the matched event's `start_time` against the trigger's own timestamp instead of just recency, or narrow the window further.
